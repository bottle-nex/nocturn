### middleware.ts

**Path**: `/Users/vaibhav_zope/Downloads/utility/nocturn/apps/web/middleware.ts`
**Bugs found**: 3

1. **[CRITICAL] Line 3: Incomplete route protection -- many authenticated routes are unprotected.** The matcher only covers `/home` and `/new/:quizId`. The `/live/*`, `/new` (root), `/premium/*`, and any future authenticated routes are completely unprotected by middleware. Any unauthenticated user can access these paths directly. **Fix**: Expand the matcher to include all routes that require authentication, e.g. `['/home', '/new', '/new/:path*', '/live/:path*', '/premium/:path*']`.

2. **[HIGH] Line 3: The pattern `/new/:quizId` does not match Next.js catch-all routes.** The actual route is `/new/[...quizId]` (a catch-all), but the middleware matcher uses `:quizId` which is an Express-style pattern. In Next.js middleware, you need `/new/:path*` to match catch-all segments properly. This means `/new/abc/def` would not be protected. **Fix**: Change to `/new/:path*`.

3. **[MEDIUM] Line 1: No NEXTAUTH_SECRET validation.** The middleware re-exports the default next-auth middleware but there is no check anywhere that `NEXTAUTH_SECRET` is configured. If it is missing at runtime, auth will silently fail or allow bypass. **Fix**: Add a runtime check for `process.env.NEXTAUTH_SECRET` in the auth options or middleware.

### app/api/auth/[...nextauth]/options.ts

**Path**: `/Users/vaibhav_zope/Downloads/utility/nocturn/apps/web/app/api/auth/[...nextauth]/options.ts`
**Bugs found**: 6

1. **[CRITICAL] Lines 73-74, 84-85, 88-89: Empty string fallback for OAuth client secrets.** `process.env.GOOGLE_CLIENT_ID || ''` means if the env var is not set, an empty string is used. This silently configures a broken OAuth provider rather than failing loudly at startup. Worse, an empty `clientSecret` could lead to unpredictable auth behavior. **Fix**: Throw an error if required env vars are missing, or use a conditional provider registration pattern.

2. **[HIGH] Line 24: No NEXTAUTH_SECRET configured in authOption.** The `AuthOptions` object does not specify a `secret` property. While NextAuth will fall back to the `NEXTAUTH_SECRET` env var, if that env var is missing, JWTs will be unsigned in production. **Fix**: Add `secret: process.env.NEXTAUTH_SECRET` to the auth options and validate it exists.

3. **[HIGH] Lines 60-68: JWT token never refreshed or expired.** The JWT callback stores the user token from the backend in the JWT on initial sign-in, but never refreshes it. If the backend token expires, the session will still appear valid client-side but all API calls will fail with stale tokens. There is no token rotation or expiry check. **Fix**: Implement token rotation in the JWT callback by checking token expiry and refreshing when needed.

4. **[MEDIUM] Line 46: Backend token stored directly in JWT without encryption.** The `user.token` from the backend API is stored directly in the NextAuth JWT and then exposed to the client via the session. This means the bearer token for backend API access is visible in the browser. **Fix**: Consider encrypting the token within the JWT or keeping it server-side only.

5. **[MEDIUM] Lines 31-48: signIn callback returns false for unknown providers.** If `account?.provider` doesn't match any known provider (google, github, facebook, email-otp), the function returns `false` at line 54. This is correct security-wise, but the error handling at line 56 logs the raw error which could contain sensitive data. **Fix**: Sanitize error logging.

6. **[LOW] Line 98: OTP not rate-limited on the client side.** The credentials provider for email-otp sends the OTP directly to the backend, but there is no client-side protection against brute-force OTP guessing (e.g. rate limiting). This must be handled server-side but there is no evidence of it. **Fix**: Ensure the backend `/verify-otp` endpoint has rate limiting.
